## Implementation tests vs independent tests

Root: Settings DTO, schema migrations/store atomic persistence, get/update/preview integration, real same-query low/high harness. Engine: configured-cap snapshot admission, worker manifest/lease cap, effective min under concurrent reservations, active job unchanged. UI: shared wire migration/parsing, controlled input/error/default/cancel/apply, mock backend preserving new field. These owners write module unit tests with product code.

Quality: independent shared fixture; `e2e/phase22-sql-storage.spec.ts` once accessible selector contract stabilizes; three viewport interaction/geometry and image review after integration; independent native report review. Browser mock cannot establish disk enforcement, restart persistence in Tauri or worker snapshots.

## Native scenario and risks

Use existing deterministic isolated stress Parquet input, optimized acceptance namespace EXE and immutable input SHA. Preserve previous42 result, original settings, clipboard; restore test settings and terminate only owned processes. Start from a low configured cap64MiB with adequate overall space, then raise to1GiB or another allowed value sufficient for the **same** query's measured spill. Query must return≤1M rows and avoid an unspillable256MiB memory failure. If it still fails from memory/result cap, that is not a successful high-cap verification; choose a predefined suitable query before the comparison and keep it byte-identical across its paired runs. Record old/new configured bytes, overall/free headroom, effective allowance, status/error, result golden, sample gaps and cleanup.

Root confirmed this configurable combined spill+result byte budget **replaces** the old fixed512MiB SQL byte ceiling, up to10GiB. Do not silently retain a512MiB job/result clamp making higher settings ineffective. Memory256MiB/threads2, row cap1M and4096-column cap remain independent. UI accessible label: `SQL temporary storage per query (GiB)`. For same-query low/high verification, sorted-subquery aggregates may be optimized to discard ORDER BY; use a sort-dependent window result aggregated to a small output and verify the actual plan retains the blocking sort/window.

Required actual environment is the existing Windows Tauri/worker candidate path; no new permissions, dependencies, OS quota or deliberate physical disk exhaustion. Native failure/cancel must preserve old result/source/settings and allow normal next query. All gates pending until implementation and evidence; no PASS inferred at design time.
