# Phase22 directly typed SQL usability — test design

Mode: test design, 2026-11-07. User-authorized five-item follow-up. Root confirmed front-end-only presentation/editor changes, immutable exact SQL+bindings snapshots, separate result/plan provenance, and helpOpen local UI preference. No backend DTO/schema change for preference. This document changes no product code or existing evidence; Phase22/version0.22.0 remain, no formal promotion.

## Proposed/frozen contract

1. **Concise candidates:** property label contains its useful current SQL name; name-mode detail is SQL type only. Ordinal detail is SQL type plus original name exactly once. Do not repeat the same original name/alias in label, detail and a mandatory expanded panel. Essential qualification remains when required to distinguish tables; insertion text/quotes/physical cN unchanged.
2. **Concise JOIN:** short `Suggested JOIN` or `Ambiguous key` detail; default short `Inferred, not a verified foreign key.`. Detailed explanation is explicitly requested through initially closed `Why this JOIN?` disclosure in `.sql-completion-info`, not always expanded. Generic-key confidence/ranking and actual join insertion remain unchanged.
3. **Undeclared aliases:** no guessing which registered source `SELECT c.` means before a declaration. A small general hint explains declaring aliases in FROM/JOIN and using the actual registered table name for column exploration. Existing valid forward-FROM local aliases still resolve. No backend query/EXPLAIN while typing or new inference algorithm.
4. **Help preference:** Examples/help collapsed/open survives workspace switching and actual app restart through a lightweight namespaced local UI key. First use remains existing default open. Invalid/missing/unavailable storage falls back safely; storage failure cannot prevent SQL/editor use. Explicit toggle updates UI immediately. It neither changes AppSettingsV7 DTO nor authored SQL/history/results. Scope is current app/webview profile, not a cross-machine backend setting.
5. **Displayed output provenance:** each successful result and plan stores its submitted request snapshot `{exact SQL, table bindings}` independently. Snapshot travels through pending/first-page retry/publication and is never reconstructed from the current editor after awaiting. Current draft equality determines whether the displayed output matches it; exact SQL restoration can restore the matching state. Running edits, cancellation/failure retaining old output, alias/mode changes and late responses cannot retarget a snapshot. Output remains readable/copyable; the label is informational, not cache invalidation or an automatic rerun.

Result and plan may originate from different requests; compare each separately. Do not use only `latest runId !== result.runId`, nor a one-way global dirty bit. Keep last-attempt failure/cancel reason distinct from the result's SQL-match indicator so SQL restoration can recover matching state without erasing error history. Root freezes exact notice labels/disclosure selectors before E2E assertions.

Binding comparison must be stable under array ordering, using source identity, alias and exclusive column mode. Snapshot is the submitted binding context rather than an assertion of actual DuckDB dependencies; no new query-on-type is allowed. User source-close/result independence contract remains. Root should explicitly distinguish a binding-context change from physical source mutation; this follow-up does not infer changed file content or invalidate completed independent results.

## Independent E2E reservation and scenarios

Quality owns `e2e/phase22-editor-usability.spec.ts` once root provides stable accessibility selectors. New file only initially; old test detail-text assertions may need an explicit separate assignment, not lower checks. Reuse existing3source sql22 mock for UI states; fixed mocked rows never prove real SQL correctness.

Suggested browser sequence: make resultA, alter only editor→badge; restoreA; capture planA; executeB→plan badge independent; slow runA/editB/cancel/fail→old output preserved; mode/alias mutate+reverse; toggle help collapsed and reload; undeclared c. hint vs declared/local/actual-table exploration; concise name/cN and ON detail disclosure with no IPC. Use controlled barriers/component fakes for pending publication and page retry instead of flaky sleeps. Real native helper root-owned; actual restart preference and joined COUNT3, exact output source labels, source hashes/settings restoration verified separately.

## High-risk implementation invariants

- Snapshot must be taken before invoking backend, not at response time. Preserve it in pending result/plan and page retry. SQL changes during awaiting are normal and must not be overwritten.
- Successful EXPLAIN/ANALYZE updates plan provenance independently of previous result; ordinary Execute must not overwrite a retained plan's origin. Cancellation/failure must preserve both output objects and their own provenance.
- Alias/mode changes do not rewrite editor text; snapshot comparison should explain context change without implying old immutable result is damaged. Reverting exact context must restore equality.
- Help preference is local UI state with guarded storage access. It cannot broaden capabilities, introduce remote sync or modify backend settings JSON.
- Disclosure and completion acceptance compete for pointer/keyboard events. Opening detail must not apply a suggestion or lose the selected option; Tab/Enter policy still applies to the actual completion list, with normal accessible disclosure focus.
- Concision is not loss of semantic identity: ordinal raw name/type and ambiguous table qualification remain inspectable; no shortened/truncated value may be inserted into SQL.

Plan only at this stage. Required native/unexecuted gates remain BLOCKED until evidence; no automatic Phase completion or formal artifact promotion.
