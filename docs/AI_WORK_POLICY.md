# AI 작업 효율 정책

이 문서는 Agent 작업의 토큰과 반복 실행을 줄이면서 제품 검증 수준을 유지하기 위한 실행
규칙을 정의한다. 정확성, 보안, 데이터 무결성은 절약보다 우선한다.

## 소규모 작업의 범위와 종료 기준

2026-11-04 Storage 0.3GiB 입력 수정에 1시간 13분을 소비한 실행의 재발 방지 규칙이다.

- 시작 시 수정 범위, 완료 조건, 필요한 검증, 재빌드 필요 여부를 짧게 확정한다. 작은 수정에
  별도 Phase 계획이나 대량 artifacts를 만들지 않는다. 이미 있는 기록과 실행 도구를 우선 쓴다.
- 관련 코드에서 원인을 찾은 뒤 재현과 영향 범위를 기준으로 검증한다. 검사를 많이 실행한
  사실을 품질 근거로 삼지 않으며, 관련 없는 backend·성능·installer 검증을 추가하지 않는다.
- 현재 계약상 필수인 gate는 유지한다. 전체 검증은 적용되는 필수 gate 또는 확인된 영향 때문에
  필요할 때 코드 확정 뒤 한 번 실행한다. 실패 뒤에는 해당 범위만 재실행하며, 전체 반복에는
  새 코드 변경·새 실패·남은 위험 등 구체적인 이유가 있어야 한다.
- 요청한 수정의 정확성·데이터 무결성·보안을 막지 않는 별도 결함은 원인과 영향을 기록해
  분리한다. 필수 gate를 막는 실패는 숨기거나 기준을 낮추지 않고, 필요한 최소 범위로 해결한다.
- 완료 조건과 필수 검증을 충족하면 종료한다. 추가적인 확신을 얻기 위한 검사, 문서 복제,
  screenshot 수집, cache 정리 등을 습관적으로 붙이지 않는다.
- 설명이나 문서 수정만 요청받은 작업에는 제품 테스트·빌드를 실행하지 않는다.

## 실행 환경과 승인 재사용

- 무거운 검증 전에 필요한 실행 파일·버전·브라우저·cache·빌드 경로를 한 번 확인한다.
  작은 재현으로 환경이 동작하는지 확인한 뒤 전체 suite를 실행한다.
- 실패를 제품 오류와 도구·경로·sandbox·네트워크 오류로 먼저 구분한다. 새 근거나 환경 변화
  없이 같은 명령을 반복하지 않는다. 환경 복구가 별도 작업으로 커지면 영향과 남은 검증을
  보고하고, 진행 가능한 원래 작업을 먼저 끝낸다. 미실행 검증을 PASS로 바꾸지 않는다.
- 빌드·테스트·일반 개발 의존성 설치·프로젝트 검증 실행은 이미 허용된 범위에서 다시 묻지
  않는다. 승인된 명령을 다른 작업과 묶거나 불필요하게 바꿔 승인 재사용을 깨뜨리지 않는다.
- 명령의 준비·실행·후처리는 필요한 경우 분리한다. 시스템이 강제하는 승인만 요청하고
  차단한 구체적인 작업과 이유를 설명한다. 승인 회피를 위해 보안 정책을 우회하지 않는다.
- 로컬 개발 검증의 실행 진입점은 `node scripts/dev-check.mjs TASK [FILTER]`로 고정한다.
  환경변수·로그 리디렉션·실행 후 처리를 바깥 PowerShell 명령에 덧붙이지 않는다.
  `--list`로 허용 작업을, `--dry-run TASK`로 실제 실행 계획을 확인할 수 있다. 동일 개발 검증
  범위의 실행 승인이 필요하면 이 스크립트의 명령 prefix 재사용을 요청한다. 승인 저장 여부와
  범위는 실행 환경이 결정하므로 승인 창이 영구히 없어졌다고 주장하지 않는다.
- `dev-check.mjs`는 frontend/backend 검사·테스트, browser E2E, 현재 native variant 빌드와
  지정된 native Storage 검증만 실행한다. 네트워크 설치, Git stage·commit·restore·push,
  사용자 파일 삭제, 배포,
  임의 shell 실행이나 보안 정책 변경을 이 승인 범위에 숨겨 추가하지 않는다. 검증 자체가
  기존에 생성·정리하던 임시 파일과 테스트 앱 설정 복원 동작은 유지한다.
- source·자산·빌드 설정·실행 메타데이터가 확정된 뒤 최종 빌드한다. 테스트·문서·증거 정리만
  바뀌면 실행 파일을 다시 빌드하지 않는다. 재빌드에는 실제 산출물에 영향을 주는 변경이나
  확인된 빌드 환경 문제라는 이유가 있어야 한다.
- 검증 출력은 처음부터 필요한 로그 파일에 저장하고 요약만 읽는다. 기존 Phase 증거를
  덮어쓰지 않도록 출력 경로를 미리 정해, 나중에 복원 작업이 생기지 않게 한다.
- 남은 작업을 확인하지 않고 “마지막 확인”이라고 보고하지 않는다. 범위나 검증 비용이
  늘어나면 이유와 남은 단계를 알리고, 요청 범위를 벗어났는지 다시 판단한다.

## 컨텍스트 수집

- 먼저 `rg`로 위치를 찾고 필요한 파일과 줄 범위만 읽는다.
- 전체 파일, 전체 diff, 대형 JSON, benchmark 원본 로그를 반복해서 출력하지 않는다.
- 실패 로그는 테스트 이름, 오류 핵심, stack의 관련 프레임과 마지막 30~50줄을 우선 수집한다.
- 이미 확인한 계약과 변경되지 않은 모듈은 다시 읽지 않는다.

## 구현과 검증 순서

1. 구현 중에는 변경 모듈의 관련 unit/component test만 실행한다.
2. UI 변경은 개발 중 영향받는 Playwright spec 또는 viewport project만 실행한다.
3. 통합 시 영향받는 frontend 또는 Rust test 묶음과 lint/typecheck/clippy를 실행한다.
4. 코드가 확정된 뒤 전체 test suite와 `npm run test:e2e`를 한 번 실행한다.
5. release/NSIS build와 최종 GUI screenshot은 모든 코드 수정이 끝난 뒤 한 번 실행한다.
6. 최종 build 뒤 코드가 바뀌면 영향 테스트와 build만 다시 실행하고 이유를 기록한다.

전체 검증 실패 시 실패한 범위만 수정·재실행하고, 매 수정마다 전체 suite를 반복하지 않는다.
서로 독립적인 검사만 병렬 실행하며 package manager, formatter, lockfile 변경은 동시에 실행하지
않는다.

## Agent와 리뷰

- 단일 소유자가 처리할 수 있는 작업에는 subagent를 추가하지 않는다.
- 기본 상한은 `주담당 1 + 협업 0~2 + 품질 1`이며 실제 독립 작업이 있을 때만 병렬화한다.
- 리뷰 지적은 가능한 한 모아서 한 번에 수정하고 한 번에 재검토한다.
- Agent handoff는 변경 파일, 테스트 결과, 결함과 남은 위험만 요약하고 원본 로그를 복제하지 않는다.

## 사용자 보고

- 중간 보고는 시작, 범위나 위험의 중요한 변경, 장기 작업 상태, 완료 시점에만 한다.
- 명령 출력 전체를 전달하지 않고 PASS/FAIL, 개수, 핵심 오류와 산출물 경로만 알린다.
- 같은 사실과 계획을 반복 설명하지 않는다.
- 최종 보고는 구현, 검증, 실행 경로, BLOCKED 항목을 우선한다.

## 문서와 산출물

- 사용자가 정식 Phase 승격을 지시하면 해당 `artifacts/phase-N/`에 범위·설계 결정·테스트·결과·검토를
  연결하고 개발 계획·제품 명세·현재 링크와 경로를 함께 정리한다. 대체된 이번 작업의 독립 폴더는
  이동·동일성·참조 확인 뒤 제거하며 과거 다른 Phase 이력은 유지한다.
- EXE는 artifacts에 보관하지 않고 `src-tauri/target/release/data-viewer.exe`에 둔다. artifacts에는
  실행 파일의 실제 위치·크기·해시·내장 버전을 기록한다. Phase 번호와 대응 버전은 함께 관리하되,
  재빌드 금지 지시가 있으면 기존 EXE와 제품 버전을 변경하지 않고 차이를 명시한다.
- Phase 전용 fixture는 `fixtures/phase-N/`에 모으고 생성기·실행 harness·Git 제외 규칙·문서 링크를 함께 맞춘다.
  과거 Phase 공용 입력은 기존 소유 경로를 유지한다. artifacts에는 원시 검증 증거와 fixture 경로·해시를 둔다.
  여러 테스트가 사용하더라도 experiment 폴더를 공용 fixture의 정식 위치로 간주하지 않는다.
- 문서·파일 정리 지시만으로 제품 코드 수정·원래 manifest 교체·재빌드·전체 테스트를 추가하지 않는다.
  이미 검증된 파일을 이동하는 경우 해시와 필요한 경로 참조만 검증한다.

- 정식 artifacts 승격은 작업 완료 후 사용자에게 한 번 확인한 뒤 수행한다. 사용자에게
  결과·검증·남은 제한·대상 실행 파일을 먼저 제시하며, 답변 전에는 draft로 둔다. 구현이나
  테스트 실행의 사전 허용은 정식 편입·정식 EXE 교체 허용을 뜻하지 않는다. 명시적으로 정식
  승격을 요청받은 결과는 추가 확인 없이 처리한다. 외부 게시 승인은 이와 별개다.
- native 빌드의 기본 결과는 experiment 경로의 draft `data-viewer.exe`다. 사용자 승격 승인
  없이 `src-tauri/target/release/data-viewer.exe`와 정식 build metadata를 교체하지
  않는다. 승인된 승격을 빌드와 함께 수행할 때만 `-PromoteArtifacts`를 명시한다. 이미 검증된
  draft의 승격을 위해 같은 코드를 재빌드하지 않는다.
- 구현 중 문서를 계속 고치지 않고 계약 변경 또는 최종 결과가 확정됐을 때 묶어서 갱신한다.
- benchmark 원본은 artifact에 저장하고 대화와 통합 문서에는 측정값과 판정만 요약한다.
- 생성 cache, 임시 fixture, 중간 screenshot은 최종 증거가 아니면 정리한다.
- 정식 승격 뒤에는 승격본과 해시가 같은 원래 증거·fixture·실행 파일 사본을 삭제하고,
  남겨 둔 정식 경로를 기록한다. 현재 빌드·테스트에 필요한 소스와 harness, 내용이 다른
  파일은 중복 정리 대상으로 삭제하지 않는다. 과거 harness 재현에는 필요한 보관 파일만 복원한다.
- 기본 release 빌드는 빠른 후속 빌드를 위해 Cargo release 중간 산출물을 유지한다. 사용자가 요청한 때에만
  `npm run clean:release`로 정리한다. release 빌드 후에는 `npm run clean:temp`를 실행해 workspace
  `.tmp`의 64MiB 이상 생성 항목이 누적되지 않게 한다.

## 절약보다 우선하는 경우

다음 상황에서는 필요한 추가 분석과 재검증을 생략하지 않는다.

- 데이터 손상, 보안 권한, 경로 검증 또는 임시 파일 정리 문제
- document/session/query identity와 비동기 경쟁 조건
- 공통 DTO, format registry, query engine처럼 여러 모듈에 영향을 주는 변경
- release에서만 나타나는 native, installer, clipboard 또는 WebView 문제
- 재현되지 않는 실패나 HIGH/MEDIUM 독립 리뷰 결함

이 정책은 테스트 수나 완료 기준을 줄이는 규칙이 아니다. 동일한 증거를 더 적은 반복과 더 작은
출력으로 수집하는 규칙이다.
