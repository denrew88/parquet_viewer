# Phase 22 — DuckDB SQL 작업 공간 검토안

작성일: 2026-11-06

상태: **초기 설계 검토 기록. 완료 판정·정식 artifacts 승격 문서가 아니다.**
이후 사용자 승인으로 Phase22 구현을 시작했다. 최신 확정 계약은
[범위](../artifacts/phase-22/00-scope.md)와 [DTO 계약](../artifacts/phase-22/05-contract.md)을 따른다.
아래 초기 제안보다 다음 확정사항을 우선한다.

- 파일별 SQL 컬럼 참조는 원본 이름 또는 c번호(c1,c2…) 중 하나만 노출한다.
- 완전한 원본 헤더에 중복·blank가 없으면 이름 모드가 기본, 있거나 헤더가 없으면 c번호가 기본이다.
- 테이블별 라디오로 둘 중 하나만 선택한다. 이름 모드가 불가능하면 이유를 표시한다.
- c번호는 원본 순서 고정이며 Skip/hide/reorder로 재번호를 붙이지 않는다.
- 테이블 목록과 선택한 테이블의 검색·가상화 컬럼 목록을 분리한다.
- 별칭은 이름 더블클릭/연필 버튼으로 바로 수정한다. 모드·별칭 변경은 기존 SQL을 자동 수정하지 않는다.
- 예제·작성 가이드는 현재 파일별 모드를 반영하며 예제를 넣어도 자동 실행하지 않는다.

## 1. 목표와 첫 범위

열어 둔 로컬 CSV·Parquet 파일을 테이블로 등록하고, 사용자가 DuckDB SQL을 작성해
JOIN·집계·계산·윈도 함수 결과를 탐색하고 복사할 수 있게 한다.
예상 실행계획과 실제 실행 분석도 제공한다.

| 첫 범위 | 후속 검토 |
| --- | --- |
| SQL 작업 탭 하나, 동시에 실행되는 SQL 작업 하나 | 여러 SQL 탭·실행 이력·SQL 저장 |
| 단일 SELECT 또는 SELECT로 끝나는 CTE | 여러 문장 실행·사용자 DDL·DML |
| 열린 CSV·Parquet 등록과 별칭·스키마 표시 | 원격 데이터·직접 경로 입력·HDF5 연결 |
| JOIN·집계·계산·윈도 함수 | 임시 테이블을 사용자가 만드는 스크립트 |
| 결과 페이지·셀 선택·TSV 복사 | 결과 내 별도 필터·정렬·Column values |
| EXPLAIN / EXPLAIN ANALYZE | 자체 예상 cost·실행 시간 예측 |
| 자원 제한·취소·오류 복구 | ART 인덱스·가속용 데이터 복제 |

단일 SELECT 허용은 모든 함수가 안전하다는 뜻이 아니다. 파일·네트워크·확장 접근 제한은
문장 검사와 별도로 적용한다. 기존 엔진과 그리드·캐시를 재사용하고 대형 의존성 추가는 전제하지 않는다.

## 2. 화면과 기본 사용 흐름

기존 파일 탭과 같은 앱 창 안에 SQL 작업 탭을 추가한다.

```text
Data Viewer
파일 탭: orders.csv | customers.parquet | SQL
┌──────────────────┬────────────────────────────────────────┐
│ 등록 테이블       │ SQL 편집기                              │
│ orders           │ 실행 / 취소 / 예상 계획 / 실제 분석      │
│  컬럼·SQL 타입    ├────────────────────────────────────────┤
│ customers        │ 결과 | 실행계획 | 메시지                 │
│  컬럼·SQL 타입    │ 결과 그리드 또는 실행계획 트리            │
└──────────────────┴────────────────────────────────────────┘
상태: 실행 상태 / 결과 행 수 / 작업 공간 사용량
```

1. 사용자가 기존 파일 열기 기능으로 CSV·Parquet를 연다.
2. SQL 탭의 등록 목록에서 테이블 이름, 실제 경로, 스키마와 준비 상태를 확인한다.
3. 테이블·컬럼 이름을 더블클릭해 편집기에 삽입하거나 SELECT 예제를 넣는다.
4. SQL을 작성하고 실행한다. Ctrl+Enter는 커서가 속한 문장 하나를 실행한다.
5. 완료된 결과를 페이지로 읽고 논리 좌표로 선택해 복사한다.
6. 필요하면 예상 계획 또는 실제 분석을 별도 실행한다.

편집기에는 구문 강조, 행 번호, 오류 위치 표시를 제공한다. SQL 편집기 선택 영역 실행과
고급 자동완성은 첫 범위의 필수 조건으로 두지 않는다. 기본 실행은 편집기의 단일 문장이다.
완료율을 알 수 없는 작업에는 임의 퍼센트 대신 상태·경과 시간을 표시한다.
좁은 창에서는 테이블 목록을 접거나 위쪽으로 배치하고, 실행·취소와 상태를 유지한다.

## 3. 파일 등록과 입력 스냅샷

| 항목 | 제안 계약 |
| --- | --- |
| 별칭 | 파일명 기반. 충돌 시 orders_2처럼 구분하며 사용자가 변경 가능 |
| 이름 삽입 | 공백·예약어·따옴표를 올바르게 인용한 식별자 삽입 |
| 입력 범위 | 기본적으로 파일 전체. 메인 화면 필터·정렬은 SQL에 자동 적용하지 않음 |
| 준비 상태 | CSV 변환 중·사용 가능·오류·사용 불가를 구분 |
| 원본 | 읽기 전용. SQL 화면 진입 때문에 CSV 전체를 다시 변환하거나 복제하지 않음 |
| 실행 고정 | 파일 identity, session, CSV profile generation을 실행 시작 시 고정 |
| 사용권 | 실행이 끝날 때까지 입력 cache lease 유지 |
| 변경·닫기 | 진행 중 입력 교체를 막거나 변경을 다음 실행에 반영. 활성 작업의 입력을 몰래 교체하지 않음 |

현재 그리드 필터 결과를 쿼리에 쓰는 기능은 별도의 이름을 가진 입력으로 명시적으로 등록하는
후속 기능으로 검토한다. 원본 변경 감지와 session 무효화는 기존 계약을 계승한다.

## 4. SQL 타입과 CSV 원문 보존

현재 표시용 문자열·상태 표현을 그대로 SQL 컬럼으로 노출하면 숫자 비교·SUM·JOIN이 잘못될 수 있다.
CSV profile에 맞는 typed SQL 입력 계층이 필요하다. 표시용 변환과 SQL 계산용 값을 구분한다.

| 상태 | 제안 정책 |
| --- | --- |
| 정상 숫자·날짜 | 대응하는 DuckDB SQL 타입 |
| text의 빈 문자열 | 빈 문자열 유지 |
| profile이 정한 null token | SQL NULL |
| 숫자·날짜 변환 실패 | NULL로 제공하되 컬럼별 실패 존재·개수와 원문 확인 경로 제공 |
| 표현 범위 초과 | 조용한 반올림·단위 변경 금지. 지원 제한 또는 명시적 변환 안내 |

변환 실패를 NULL로 제공하면 SUM 등에서 제외되므로 실행 결과에 그 사실을 알린다.
실패 개수는 신뢰할 수 있는 준비 통계를 재사용하고, 실행마다 경고 집계를 위해 전체 파일을
추가 스캔하지 않는 방식을 우선 검토한다. 원문 SQL 노출 이름·형식은 아직 확정하지 않는다.

- 64비트 정수·decimal은 JavaScript Number를 경유해 정밀도를 잃지 않는다.
- timestamp의 정밀도·시간대, timedelta의 단위와 DuckDB INTERVAL의 차이를 검증한다.
- Parquet의 논리 타입과 DuckDB 지원 범위가 다르면 명시적으로 처리한다.
- 결과의 duplicate 컬럼명·NULL·긴 문자열·BLOB·nested 타입은 별도 내부 ID와 타입별 표시로 다룬다.
- 지원하지 않는 결과 타입은 무조건 문자열로 바꿔 의미를 숨기지 않는다.

## 5. 임의 SQL 결과 데이터 소스

현재 결과 인덱스는 `query_result(__dv_row_id)`를 만들고 원본에서 값을 가져온다.
JOIN·집계·계산 결과에는 이 구조를 그대로 사용할 수 없다.

새 SQL 결과는 결과 ID, 실행 generation, schema, 컬럼 내부 ID, 행 순번과 실제 값을 소유한다.
같은 표시 이름의 두 컬럼도 독립적으로 조회·선택·복사할 수 있어야 한다.

권장 초기 구조:

```text
단일 SQL 실행 → bounded batch로 결과 저장 → 검증된 결과 공개
                                      → 페이지 조회 / 가상화 / 선택 / 복사
```

결과는 앱이 관리하는 임시 저장소에 보관한다. DuckDB 임시 DB와 chunk 저장 등 구체적인
형식은 작은 PoC에서 처리량·공간·임의 페이지 비용을 비교해 결정한다.
전체 결과를 Rust Vec나 JSON 배열 하나로 만들거나 WebView로 한 번에 전달하지 않는다.
페이지마다 원래 SQL을 다시 실행하지 않는다. 결과 앞·중간·끝 탐색 비용도 검증한다.

실행 결과 안에서는 행 순서를 고정한다. ORDER BY가 없는 SQL의 실행 간 순서는 보장하지 않는다.
결과 헤더 클릭으로 원래 SQL을 자동 재작성하는 기능은 첫 범위에서 제외한다.
복사는 기존 TSV escape·셀/바이트 한도·취소·원자적 clipboard commit 계약을 재사용한다.

## 6. 작업 생명주기와 취소

```text
입력 준비 → SQL 검사 → 실행 중 → 결과 저장 → 완료
                         └→ 취소 / 실패 → 소유 임시 데이터 정리
```

- 한 SQL 작업 공간에서 동시에 실행되는 작업은 하나로 제한한다.
- execute, explain, analyze 모두 동일한 실행 제한·취소·오류 경로를 사용한다.
- 오래된 응답은 현재 editor/run/result generation을 덮어쓰지 못한다.
- 새 쿼리가 실패하면 직전 성공 결과를 보존하는 방향을 우선한다.
- 구 결과와 새 결과를 동시에 보유하는 동안은 둘 다 디스크 예산에 포함한다.
- 공간이 부족할 때 사용자가 이전 결과를 명시적으로 비울 수 있어야 한다.
- 취소는 interrupt 요청 후 worker 종료와 정리를 확인한다. 정상 응답하지 않는 worker의 강제
  종료·복구 경로도 검토하며, 다른 Viewer 프로세스를 종료하지 않는다.

같은 EXE의 worker 모드로 SQL 실행을 분리하는 방안을 우선 검토한다.
프로세스 분리는 충돌·취소 대응에 유리하지만 그 자체가 OS 보안 sandbox는 아니다.
입력 등록·lease·예산을 프로세스 경계에서 어떻게 유지할지 먼저 검증한다.

## 7. 자원과 디스크 예산

```text
전체 관리 사용량 = 재사용 CSV cache + query 작업 파일 + SQL 결과 저장 + 기타 관리 데이터
```

전체1GiB 중 cache가388MiB라면 약636MiB만 남는다. 이 잔여량도 작업 spill과 결과가 공유한다.
이는 산술 예시이며 실행 가능한 쿼리 크기 보장이 아니다. 물리 디스크 안전 여유와
실제 allocation·예약량도 별도로 확인한다.

| 자원 | 필요한 제어 |
| --- | --- |
| RAM | DuckDB memory_limit, bounded batch, worker 메모리 감시 |
| CPU | threads 제한, 앱 응답성, 취소 |
| 작업 파일 | max_temp_directory_size와 앱 예산 예약·실측 |
| 결과 | 저장 바이트·행 수 상한. 구/새 결과 동시 사용량 포함 |
| IPC | 페이지 행 수·값 길이·응답 바이트 상한 |
| 물리 공간 | C/D 등 각 volume별 실제 여유와 안전 reserve |

DuckDB memory_limit은 전체 프로세스 RAM의 절대 상한이 아니다.
SQL 결과 DB·WAL 등이 생기면 spill 한도만으로 전체 저장량을 제한할 수 없다.
worker의 결과 저장과 앱 storage manager의 예약·정리를 함께 연결해야 한다.

상한 도달 시 일부 결과를 전체 결과처럼 공개하지 않는다. 초기 버전은 실행 실패로 처리하고
조건·projection·LIMIT 조정을 안내한다. SQL에 LIMIT을 몰래 추가하지 않는다.
기본 SELECT 예제에만 LIMIT1000을 명시한다. LIMIT이 모든 중간 연산의 비용을 제한하지는 않는다.

CSV cache 위치와 SQL 작업·결과 위치는 구분한다. cache가D에 있어도 query temp가C일 수 있다.
SQL 임시 위치를 별도 설정할지, 기존 query-temp 위치를 따를지는 구현 전 확정한다.

## 8. 예상 계획과 실제 분석

| 액션 | 의미 |
| --- | --- |
| 실행 | SQL 결과 생성·저장·탐색 |
| 예상 계획 | EXPLAIN. 일반 쿼리 결과 생성 없이 예상 연산 구조 확인 |
| 실제 분석 | EXPLAIN ANALYZE. 실제 실행 후 연산별 통계 확인 |

계획은 트리와 원본 텍스트로 표시하고 복사를 제공한다.
노드 선택 시 연산 종류·조건·projection·예상 행 수와 제공되는 실제 행 수·시간을 보여준다.
없는 항목은 0으로 채우지 않고 미제공으로 표시한다.

실제 분석은 무거운 작업일 수 있으므로 버튼에 실제 실행임을 명확히 표시한다.
분석 요청에 일반 SELECT를 별도로 추가 실행해 같은 SQL을 두 번 돌리지 않는다.
초기 analyze는 계획·통계를 제공하는 작업으로 구분하며 SELECT 결과 동시 제공을 약속하지 않는다.
결과 저장을 추가하는 방식은 분석 시간에 앱의 materialization 비용이 섞이는지도 검증해야 한다.

병렬 연산의 노드 시간 합은 전체 경과 시간과 같지 않을 수 있다.
Oracle식 노드별 예상 cost·초 단위 예측은 첫 범위에서 제공하지 않는다.
UI 시안의 실행계획과 수치는 예시이며 실제 DuckDB 출력·측정 결과가 아니다.

## 9. 읽기 전용 실행 경계

SQL을 Rust prepare에 넘기기 전에 문장 개수와 문장 종류를 검사한다.
정규식·첫 단어 검사에 의존하지 않는다. SELECT 내부 함수의 파일 접근도 통제한다.

- 등록된 입력에 필요한 정확한 파일만 허용하는 정책을 검토한다.
- COPY·ATTACH·DDL·DML·SET·PRAGMA·INSTALL·LOAD 등 사용자 제어 명령을 제한한다.
- 확장 자동 설치·자동 로드와 네트워크 접근을 제한하고 configuration을 잠근다.
- 파일 허용 목록은 읽기 전용 권한 자체가 아니므로 문장·함수·경로 검증을 함께 적용한다.
- 내부 입력 등록과 결과 저장은 앱이 생성한 신뢰된 명령으로 분리한다.
- EXPLAIN으로 감싼 위험한 입력과 여러 문장도 검사한다.
- 설정 제한과 별도 프로세스만으로 완전한 sandbox라고 주장하지 않는다.

## 10. 개발 순서와 완료 확인

아래는 Phase 내부 작업 순서 제안이며 새 공식 Phase 번호를 만드는 것이 아니다.

| 순서 | 개발 | 핵심 확인 |
| --- | --- | --- |
| 1 | 입력 등록·SQL 타입·문장 검사 계약 | CSV/Parquet 혼합 JOIN, 타입 정밀도·변환 실패 정책 |
| 2 | worker·단일 실행·결과 데이터 소스 PoC | 한 번 실행, bounded 저장, 앞/중간/끝 조회 |
| 3 | 예산·취소·실패 복구 | 작은 storage, 큰 결과, 취소 후 정리·이전 결과 보존 |
| 4 | SQL 화면·결과 선택·복사 | 키보드, 중복 컬럼명, stale 응답, 전체/부분 복사 |
| 5 | 예상 계획·실제 분석 | 실제1회 실행, 통계 누락 처리, 트리/원문 일치 |
| 6 | 통합 검증 | 실제 Tauri, 여러 창의 합산 예산·lease·종료 정리 |

필수 테스트 후보:

- inner/left JOIN, 중복 키·NULL 키·일대다·빈 결과·다대다 결과 폭증.
- GROUP BY·window·DECIMAL·UInt64 max·2^53 인접값·timestamp 정밀도·시간대·duration.
- CSV null/empty/invalid, profile 교체·원본 변경·탭 닫기와 실행 경쟁.
- 대용량 결과의 페이지 왕복·TSV 정확성·긴 셀·nested/BLOB·중복 컬럼명.
- 실행/저장/복사 중 취소, worker 종료, 늦은 응답 차단, 임시 파일·lease 회수.
- 전체1GiB 및 경계 한도, cache와 spill·구/새 결과 합산, C/D 물리 공간 부족.
- 복수 문장·주석·인용·CTE·SELECT 내부 파일 함수·설정 변경·확장·경로 우회.
- 예상 계획과 실제 분석의 실행 횟수·취소·오류. 누락 지표를 가짜 숫자로 표시하지 않음.
- UI 구현 시 프로젝트 UI_VALIDATION/PLAYWRIGHT 계약의 interaction·geometry·세 viewport·실제 Tauri.

문서와 UI 시안 작성은 위 기능을 구현하거나 완료 조건을 통과한 것으로 간주하지 않는다.

## 11. 구현 전 확정할 결정

1. 잘못된 typed 값의 NULL 변환 안내와 원문 확인 UI.
2. timestamp·duration·Parquet 확장 타입의 SQL 대응표.
3. 결과 저장 형식과 행/바이트 상한·이전 결과 보존 정책.
4. SQL worker의 메모리·threads·timeout 및 종료 정책.
5. query temp/result 위치와 cache를 포함한 여러 프로세스 예산.
6. 닫힌 파일의 등록 유지와 SQL 입력 lease 해제 시점.
7. 등록 입력을 허용하면서 임의 파일 접근을 차단하는 DuckDB1.5.4 정책의 검증.
